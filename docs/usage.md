# Usage

The in-app **Guide** covers the same ground for staff. This page is the reference version.

## Main flow

1. **Delivery:** set the date and who received it. Optional: expected pallets, trailer number, seal in, seal out (the three boxes sit side by side only when the Delivery card is at least 520px wide, enough for an 11-character seal number in each; otherwise the trailer box is full width with the two seal boxes under it, since build 45), notes (up to 2000 characters). Previously used names appear as one-tap buttons. For the next trailer on the same day, **Clear trailer, seals and notes** under the notes box empties those four boxes and keeps the rest (build 53, see [below](#clear-trailer-seals-and-notes-build-53)). Since build 48, if seal in and seal out are the same number, or have different lengths (spaces and upper/lower case are ignored), a note under the seal boxes asks you to check them (see [Seal check](#seal-check-build-48)).
2. **Manifest (optional):** open **Manifest check** and add the manifest by photo, PDF or typing, before scanning.
3. **Log pallets:** choose the type (BB, FMCG, FPP, Mixed), tick FSDU if needed, scan or type the LPN, press Add or Enter.
4. **Export:** **Export → Download (Excel)**, **Email PDF** or **Print**. The log then shows "Exported at hh:mm" and offers **Start a new delivery?**
5. **Start new delivery:** saves the delivery to Saved deliveries and clears the page (Undo is offered). If the delivery hasn't been exported since its last change, the first press shows a reminder; pressing again goes ahead.

If the app is opened on a later day with a delivery that has pallets but was never exported, a reminder card at the top offers **Export now** (build 62, see [Reminder about a delivery not exported](#reminder-about-a-delivery-not-exported-build-62)).

## Logging behaviour

- The type stays selected after each pallet (unless "Keep the last pallet type" is off); FSDU clears each time.
- Before adding, an LPN is checked. A warning with **Skip / Add anyway** appears when it is:
  - already in the log;
  - not 1–3 letters followed by digits;
  - using a prefix outside the prefix list;
  - the wrong number of digits: 9 or 10 for most LPNs (usually 3 letters), but 10 or 11 for `IM` numbers (full pallet picks, 2 letters). The warning says, for example, "has 12 digits (usually 9 or 10)" or, for `IM`, "has 9 digits (IM numbers have 10 or 11)". Since build 39 an 11-digit `IM` number is not warned about.
- While a warning is waiting for an answer, another LPN typed or scanned into the box (a hardware scanner presses Enter on its own) is not lost and not added: it stays in the box, selected, with the message "Answer the check first (Skip or Add anyway), then add <LPN>." and the warning sound. After Skip or Add anyway, press Enter (or Add) to add it; the next scan replaces it, because it is selected. Since build 41.
- **Escape** skips a waiting warning, the same as **Skip**. It does nothing while the Guide, Changelog, Settings or Saved deliveries panel or the install box is open, or while another box (for example an LPN being edited in the table) has the keyboard; it does work in the LPN box.
- Each add shows "Added #n: LPN · type", plus "✓ on manifest" or "⚠ NOT on manifest" while a manifest is loaded.
- On phones the entry bar shows `n logged`, `n of expected logged`, or `n of total on manifest`, and the Delivery card folds into one line once logging starts. Since build 56 the count uses the longest wording that fits the bar and is never cut off: with an expected number it tries `n of x logged`, then `n/x logged`, then `n/x`, then just `n`; with a manifest `n/total on manifest`, then `n/total`, then `n`; otherwise `n logged`, then `n`. It is chosen again when the phone is turned or the text size changes. Screen readers always hear the full wording (for example "12 of 40 logged"). Before build 56 it switched to the short form on any screen under 400px. On screens under 360px the gaps around the FSDU box, the count and ↶ are a little smaller to give the count room.
- The ↶ button next to the entry-bar counter (phones only) removes the most recent pallet, with Undo.
- Tap an LPN to edit it (each LPN is a button, so it can also be reached with Tab and opened with Enter or Space); Enter saves, Escape cancels, and since build 42 both put the keyboard back on that LPN. Change type or FSDU in the table; ✕ removes it. Undo appears after removing, editing or Clear all; since build 55 one edit gives one Undo bar for everything changed in it (LPN, description, damage and, since build 62, refused). Since build 62 the last 10 changes can be undone in turn (see [Undo for the last 10 changes](#undo-for-the-last-10-changes-build-62)). Tapping an LPN also opens the damage choices under it (see [Damaged pallets](#damaged-pallets-build-49)), the **Refused (sent back)** button after them (build 62, see [Refused pallets](#refused-pallets-build-62)), and the Description box for a pallet with no LPN, an FPP pallet (since build 56) or any pallet with a description (see [Pallets with no LPN](#pallets-with-no-lpn-build-55) and [FPP pallet descriptions](#fpp-pallet-descriptions-build-56)). Since build 56 the LPN edit box is at least 44px tall (38px before).
- **Undo bar:** shows the newest change that can be undone, with "(n earlier)" after it when there are older ones (build 62). It stays 20 seconds (9 before build 42), and doesn't go away while it has the keyboard focus. On phones (under 760px) it floats just above the entry bar, so it can be seen while logging; with the Manifest check open (the entry bar stepped aside) it shows at the top of the screen instead (since build 45; before, it sat near the bottom and could cover a results row), so it never sits over the results being worked on. While the Undo bar shows, the "Added" note appears above it instead of underneath; a new Undo bar hides any "Added" note that is showing.
- Search and the type and FSDU filters only change what is shown; totals always cover the whole log. FSDUs are counted separately and are not part of the total. Since build 62 refused pallets are left out of the total and the type counts too, and a **Refused** count (its number in the warning colour) is added after FSDU when there are any; the FSDU count only counts pallets that weren't refused.
- With Expected pallets set, the line under the totals reads "n of x expected" (counting every pallet in the log, refused ones included, since they came off the trailer) with "(n to go)" in the normal text colour while counting, turns green with "✓ all accounted for" when the count matches, and turns red with "(n more than expected)" only when there are more pallets than expected. When a manifest is loaded and Expected pallets equals the manifest count, this line is hidden, because the manifest progress line already shows the same count.
- On phones (under 760px wide) the pallet table has no scroll box of its own: it scrolls with the page, and the column headings stay pinned at the top of the screen while you scroll through it. Long LPNs wrap onto a second line instead of pushing the page sideways. On wider screens the table keeps its own scroll area (up to 60% of the screen height).
- The FSDU tick boxes in the table are 32px. On phones the FSDU tick box in the entry bar is 40px and the scan option buttons (Live scan, Scan by photo, Upload photo since build 64, No LPN) are at least 48px tall, for gloves (build 41; before, 32px and 42px). The Guide, Changelog and Settings buttons in the header are at least 44px tall on phones.
- On screens up to 620px wide the header buttons wrap onto a second line and share the row (each sized to its text) instead of pushing the page sideways, for example with Extra large text.
- On phones, a box or button that gets keyboard focus scrolls clear of the fixed entry bar instead of ending up behind it.

## Damaged pallets (build 49)

Tap an LPN in the log (or Tab to it and press Enter). As well as the LPN box for correcting the number, a row opens under the pallet: **Damage:** **None**, **Crushed**, **Wet**, **Other…**.

- **Crushed** or **Wet** marks the pallet straight away and closes the row.
- **Other…** shows a box ("What’s wrong?", up to 60 characters) with **Save**; Enter in the box saves too. An empty box isn't saved. If the pallet already has a note of its own, **Other…** opens with that text in the box.
- **None** removes the note.
- The current choice is shown pressed (red for a reason, normal for None).
- A change to the LPN typed in the box at the same time is saved together with the damage choice. **Escape** cancels both. Since build 55 both changes (and a description change) are named on one Undo bar and undone together.

A damaged pallet shows "Damaged: <reason>" in red under its LPN, with a red line on the left of the LPN cell; a long note wraps instead of widening the table. The Undo bar says "Marked <LPN> as damaged (<reason>)" or "Damage note removed from <LPN>", and **Undo** puts the old note back. The note is saved with the log, in saved deliveries and in backups. Changing it after an export counts as a change, so the log reads "Changed since it was exported…" and Start new delivery asks for a fresh export.

On exports each damaged pallet gets a row "Damaged pallet | <LPN>: <reason>" at the end of Delivery Details (Excel, the basic `.xls` and the PDF). Importing an exported log (Saved deliveries) puts the notes back on their pallets. The copy of the log in a Manifest check export doesn't include damage notes.

**Keyboard:** with the LPN box open, Tab goes to the damage choices, or to the Description box when there is one (Shift+Tab from **None**, or from the Description box, goes back to the LPN box). Leaving both the box and the choices (for example Tab past **Save**) closes them and keeps any change; when the keyboard was used, or focus would otherwise be lost because the table was redrawn, it goes back to that pallet's LPN. Since build 64 this also happens when Tab past the last choice lands on another control in that pallet's row before the table is redrawn (a slow phone or browser), so focus never ends up somewhere unexpected. On phones the row scrolls into view above the entry bar, even for the last pallet. The buttons are at least 44px tall.

Short pallets and torn wrap are not choices: the user asked for them to be taken out (see [decisions](decisions.md#damage-notes-on-pallets-build-49)). Use **Other…** for anything else.

## Refused pallets (build 62)

For a pallet that came off the trailer but was sent back with the driver. Tap its LPN (or Tab to it and press Enter): after the damage choices there is a **Refused (sent back)** button (at least 44px tall). Screen readers hear "Mark <LPN> as refused, sent back with the driver".

- **Tapping it** marks the pallet and closes the row. The Undo bar says "Marked <LPN> as refused (sent back)", and **Undo** takes the mark off. A change to the LPN box, the description or the damage made in the same edit goes on the same Undo bar.
- **In the log** the pallet stays in the table, with "Refused: sent back" in bold in the warning colour under its LPN (it wraps between words, not inside them) and a bar in the warning colour on the left of the LPN cell. Its LPN button is read as "Edit LPN <LPN>, refused, sent back…".
- **Taking it off:** tap the LPN again; the button now says **Not refused** (with a border in the warning colour). Tapping it gives "<LPN> is no longer marked as refused".
- **Counts:** a refused pallet isn't counted as received. The totals above the log, the type counts and the FSDU count leave it out, and a **Refused** count is shown on its own. The "n of x expected" line, the entry-bar counter and the Manifest check still count it, because it came off the trailer: a refused pallet on the manifest is still **Matched**.
- **A pallet can be refused and damaged** at once; both marks show.
- **Saved** with the log, in saved deliveries and in backups. Marking or unmarking it after an export counts as a change ("Changed since it was exported…").
- **On exports** (Excel, the basic `.xls`, Email PDF and Print) the pallet is still listed with its type and FSDU. The Pallet Type table's **Total** leaves it out, a "Refused (not in total)" row comes after "FSDU (not in total)" (only when there are refused pallets), and Delivery Details gets a row "Refused pallet | <LPN>: sent back with the driver", before any "Damaged pallet" rows. Importing an exported log (Excel, CSV or an app-made PDF) puts the mark back on the pallet.
- **Elsewhere:** the Manifest check's copy of the log (made from the current log, a saved delivery or an app-made PDF log) counts the same way, with its own "Refused (not in total)" row. In **Saved deliveries** the "n pallets" heading of each delivery includes refused pallets (the panel's help says so), and the line under it ends ", refused n".

The button can be switched off for everyone in the site settings (`refused`): it is no longer offered, the Guide paragraph, the "and refused pallets" part of the totals sentence and the changelog bullet are left out, but a pallet already marked keeps its mark, still shows it and is still left out of the totals. Marked as in testing, the note "In testing: Marking pallets as refused may not always work yet…" shows under the button. With `damage` switched off and `refused` on, tapping an LPN still opens a row, with only the Refused button (and the Description box when the pallet has one).

## Pallets with no LPN (build 55)

For a pallet that arrives without an LPN label. Pick the type (and tick FSDU if needed) as usual, then tap **No LPN**. It sits with **Live scan**, **Scan by photo** and (since build 64) **Upload photo** (under **Scan** on a phone), and screen readers hear it as "Add a pallet with no LPN".

- **Numbering:** the pallet is logged as "No LPN 1", then "No LPN 2" and so on: the next number is one more than the highest "No LPN n" in the log, so a removed pallet's number isn't reused while a higher one is there. The "Added" note says, for example, "Added #3: No LPN 1 · FMCG · FSDU". The type and FSDU follow the same rules as any pallet (FSDU clears afterwards; the type stays unless "Keep the last pallet type" is off). No duplicate or LPN-shape warning is shown for it.
- **Numbers stay unique:** whenever the log is saved, a second pallet with the same "No LPN n" (for example one brought back by **Undo** after a new one took its number, or one from an imported log) is renumbered to the next free number. The first one in the log keeps its number.
- **While a warning is waiting** (Skip / Add anyway), **No LPN** doesn't add anything: the message says "Answer the check first (Skip or Add anyway), then add the pallet with no LPN." with the warning sound.
- **Description:** straight after it is logged, the pallet opens for editing with the cursor in a **Description** box (placeholder "Optional: wrap, labels, PO number", up to 60 characters; screen readers hear "Description for No LPN 1"). Type what identifies it and press **Enter** to save, or **Escape** to leave it without a description (the pallet stays logged). Since build 56, Enter or Escape in a box that opened by itself puts the cursor back in the LPN box, ready for the next pallet, and Escape with text typed in the box says "Description not saved for No LPN 1." Leaving the box also saves it. Spaces are tidied and an emptied box removes the description. The Undo bar says "Description saved for No LPN 1" (or "Description removed from …").
- **A scanner in the description box:** for a pallet that has no saved description yet, a handheld scanner reading the next pallet into the box isn't kept as a description: the edit closes and the code goes into the LPN box and through the normal add, so it is logged as the next pallet (with the usual checks and warnings). Since build 56 this is decided by typing speed, not by the code's shape: it only happens when the text is at least 6 characters, is one word (no spaces), has 4 digits in a row, and arrived at scanner speed (from the first character to Enter in under 35 ms per character plus 100 ms). Anything typed by hand stays as the description, even one that looks like an LPN, such as a PO number like PO12345678. A scanned code that isn't LPN-shaped (for example a 20-digit carton code) also goes to the LPN box, where the usual warning shows. Before build 56 the rule was one LPN-shaped value (1–3 letters and 8–12 digits), however it was typed.
- **The LPN turns up later:** tap the pallet. Its LPN box is empty, with the hint "LPN if found" (screen readers: "LPN for No LPN 1, if you find one"). Type the LPN and press Enter: the pallet becomes a normal pallet (counted against a loaded manifest as usual) and keeps its description. Leaving the box empty keeps it as No LPN.
- **One Undo per edit:** everything changed in one edit (description, damage choice, LPN) goes on one Undo bar, for example "Description saved for No LPN 1. Changed No LPN 1 to VLT004040265", and **Undo** puts all of it back.
- **Damage** works the same as on any pallet: with damage on, the damage choices show under the description box. With damage switched off in the site settings, the description box still opens for these pallets.
- **Any pallet with a description** (for example one whose real LPN was typed in later) shows the Description box when it is tapped, so the text can be changed or removed.
- **In the log** "No LPN n" is shown in italic in the normal text font (not the LPN font), and a description shows on its own line under the LPN in bold, in the normal text colour.
- **Saved** with the log, in saved deliveries and in backups. Changing a description after an export counts as a change ("Changed since it was exported…").
- **On exports** each description gets a row "Pallet description | <LPN>: <description>" at the end of Delivery Details, after any "Damaged pallet" rows (Excel, the basic `.xls` and the PDF). The pallet itself is listed as "No LPN n" with its type and FSDU. Importing an exported log (Excel, CSV or an app-made PDF) puts the descriptions back on their pallets.
- **With a manifest loaded** these pallets are not counted as "not on the manifest" and get no "⚠ NOT on manifest" note or warning sound. For the Manifest check results see [Manifest check](#manifest-check).

The button can be switched off for everyone in the site settings (`noLpn`); pallets already logged with no LPN stay in the log. Marked as in testing, the note ("In testing: Logging pallets with no LPN may not always work yet…") shows in the description row of a No LPN pallet. On screens 300px wide or less (for example 200% browser zoom) the scan option buttons wrap onto two lines instead of running off the screen.

On screens under 360px wide a long description shows at most two lines under the LPN (since build 56); tap the LPN to see all of it in the box. Exports always have the whole text.

## FPP pallet descriptions (build 56)

An FPP pallet usually carries one product, so when one is logged the app asks what is on it.

- **When the box opens:** straight after an FPP pallet is logged by typing the LPN, by a handheld scanner, with **Add anyway** after a warning, or with **Scan by photo** or **Upload photo** (build 64), the pallet opens for editing with the cursor in its **Description** box. The placeholder is "What’s on it, e.g. kitchen roll" (No LPN pallets keep "Optional: wrap, labels, PO number"); screen readers hear "Description for <LPN>". With damage on, the damage choices show under it as usual.
- **Not during Live scan:** the phone's keyboard would cover the camera, so the box doesn't open by itself while Live scan is running. Tap the LPN afterwards to add a description.
- **Filling it in is optional.** Type what is on it (up to 60 characters) and press **Enter** to save it, or press **Enter** on the empty box to leave it blank. Either way the cursor goes back to the LPN box, ready for the next pallet. **Escape** closes it without saving and also goes back to the LPN box; if something had been typed, the message says "Description not saved for <LPN>." Leaving the box another way (tapping elsewhere) saves what is in it.
- **Scanning the next pallet while the box is open** logs it as the next pallet, not as the description, by the same scanner-speed rule as No LPN pallets (see [the scanner rule](#pallets-with-no-lpn-build-55)). A PO number typed by hand stays as the description.
- **Later:** any FPP pallet shows the Description box when its LPN is tapped, including one whose type was changed to FPP in the table. Other pallet types don't get the box unless they already have a description.
- **Screen readers:** a box that opened by itself is described as, for example, "Added #1: VLT004040265 · FPP. Optional: type what’s on it, or press Enter to skip and scan the next one." (No LPN pallets: "…Optional: describe the pallet, or press Enter…"), because moving the cursor can cut off the "Added" message. A box opened by tapping has no such hint. When the feature is marked as in testing, the testing note is read out with the box too.
- **The "Added" note** at the bottom of the screen doesn't cover the open box or its damage choices: the page scrolls them clear, and if it can't scroll far enough the note goes early (a warning note stays).
- **Shown, saved and exported** like any description: on its own line under the LPN, saved with the log, saved deliveries and backups, as "Pallet description | <LPN>: <description>" in Delivery Details on the Excel, basic `.xls` and PDF exports, and put back by importing an exported log.

It can be switched off for everyone in the site settings (`fppDesc`): the box then doesn't open by itself and isn't offered when an FPP pallet is tapped (an FPP pallet that already has a description still shows it), and the Guide paragraph and changelog bullet are left out. Marked as in testing, the note "In testing: Descriptions for FPP pallets may not always work yet…" shows in the description row of an FPP pallet. On a 320px screen, also with Extra large text and the testing note, the open box fits the screen without the page sliding sideways; the testing note wraps.

## Scanning

| Method | When to use |
|---|---|
| Live scan | Camera continuously adds each barcode it sees; the screen stays awake while it runs |
| Scan by photo | Fallback when live scanning is unreliable. Since build 64 it opens the camera to take a photo and reads the barcode; since build 65, when there is none, **Read the printed LPN** reads the same photo's printed number (see below) |
| Upload photo | Since build 64. Choose a photo of the label already on the phone (or take a new one), or since build 65 several photos at once; reads the barcode, and if there is none the LPN printed on the label is read instead and shown to check first (see below) |
| Hardware scanner | Focus the LPN box; the scanner types and presses Enter. Check a scanner first with **Settings → Test a handheld scanner** (build 59, see below). Since build 62 the screen stays on while the app is open, so scans aren't lost to a screen that has gone off (see below) |

"Ask me to confirm each scanned barcode" in Settings shows each scan for approval first.

**Scan by photo and Upload photo (build 64).** Since build 64 these are two buttons in the scan row (under **Scan** on a phone): **Live scan**, **Scan by photo**, **Upload photo** and **No LPN**. Either photo button stops Live scan first if it is running. The line under the camera box says "Reading barcode…" while the barcode is looked for (since build 64 it is set a moment after the camera box shows, so screen readers announce it).

- **Scan by photo** asks the phone for the back camera, so it opens the camera straight away (as before build 63). It reads the barcode. With no barcode, when **Upload photo** and reading **photos** are both switched on, it says "No barcode found. Try again closer and steadier, or use Read the printed LPN to read the number printed on the label in this photo." and shows a **Read the printed LPN** button in the camera box, next to **Stop scanning** (build 65; see below). Otherwise it says "No barcode found. Move closer, hold steady and try again." It never reads the label's printed text unless that button is tapped. (In build 64 it said "If the barcode is damaged, use Upload photo: it can read the LPN printed on the label." instead.)
- **Upload photo** opens the phone's picker without asking for the camera, so a photo already taken can be chosen; most phones also offer to take a new one there. Since build 65 several photos can be chosen at once (see "Several photos" below). It reads the barcode the same way, then, when there is none, reads the printed LPN as described below. (In build 63 this was what **Scan by photo** did, with the picker no longer forced to the camera.)
- **A check already waiting** (since build 65): if the check bar (Add or Skip) is showing when a photo's barcode is read, the barcode isn't added or asked about: "Answer the check above first (Add or Skip), then try the photo again."
- **The tip** under the buttons names only the photo buttons that are switched on: "Tip: if Live scan doesn’t work, try Scan by photo or Upload photo instead." (or just one of them). With Live scan switched off, or both photo buttons off, there is no tip.

**Read the printed LPN (build 65).** After **Scan by photo** finds no barcode, tap **Read the printed LPN** in the camera box to read the LPN printed on the label from that same photo, so it doesn't need to be taken again. It works exactly as the printed LPN reading below, except the first line says "Reading the LPN printed on the label. This can take up to a minute…". The button hides once tapped (focus moves to **Stop scanning** first, and then to **Skip** on the check that appears), and it goes when the camera box closes, Live scan starts or another photo is taken. If a check is already waiting, it says "Answer the check above first (Add or Skip), then use Read the printed LPN." and keeps the button and the photo, so tap it again after answering. It needs both **Upload photo** and reading **photos** switched on (`photoUpload` and `manifestPhotos`); without either the button never shows.

**Upload photo and the printed LPN (build 63, on Upload photo since build 64).** When no barcode can be read from an uploaded photo, and both **Upload photo** and reading **photos** are switched on in the site settings (`photoUpload` and `manifestPhotos`; in build 63 it was `scanByPhoto` and `manifestPhotos`), the app reads the LPN printed on the label with the same photo reader as the Manifest check's manifest photos. The Guide notes that this needs iOS 16 or newer on an iPhone:

- The line says "No barcode found, so reading the LPN printed on the label. This can take up to a minute…", followed by the reader's own progress (for example "Reading the printed LPN: No numbers found, so turning the photo to try again…"). The first use downloads the photo reader, as for manifest photos.
- **Never added straight away.** Printed text can be misread, so the reading always appears in the check bar with **Skip** and **Add**, even when "Ask me to confirm each scanned barcode" is off: "Read <LPN> from the printed label (no barcode found): check it matches the label. Add it as <type>?" Check it against the label, then tap **Add** (it is logged with the type and FSDU tick that were set when the check appeared) or **Skip**. The line under the camera box says "Read <LPN> from the printed label. Check it, then Add or Skip above."
- **Notes in the check bar:** ", one character corrected" is added inside the brackets when the photo reader corrected the number; "Its prefix isn’t in your prefix list." is added when a prefix list is set in the Manifest check, the LPN's prefix isn't on it and (since build 65) the usual LPN checks are off ("Warn me about duplicate or unusual LPNs before adding them" unticked in Settings). The LPN is still offered, because it is one pallet's own label. With the usual LPN checks on, any problem (already logged, prefix, digit count) is listed after it as for a typed LPN, and the button says **Add anyway**; build 64 also added the prefix note then, so the prefix was mentioned twice.
- **Which LPN is offered:** only readings shaped like an LPN (letters followed by 9 or 10 digits, or IM followed by 10 or 11) are offered, one at a time; one whose prefix is on the prefix list comes first. The same LPN printed twice on the label is offered once. Other LPNs read from the photo are named after it, up to three: "Other LPNs on the photo: … (scan them separately if they’re other pallets)." (with "…" after the third when there are more)
- **Other numbers** (order or PO numbers and the like) are never offered; they are only counted: "1 other number on the label was left out." or "n other numbers on the label were left out."
- **A number read without its letters** after "LPN:" on the label, with no LPN found: "No barcode found. A number after “LPN:” was read without its letters (<digits>): type it in with the letters at the start."
- **Nothing found:** "No barcode or LPN found. Try a clearer, closer photo of the label." (build 63 said "Move closer, hold steady and try again.")
- **Reader problems** are shown as they are, for example "The photo reader couldn’t load. Check you’re online and try again, or type the numbers in the box instead. (Reading photos needs iOS 16 or newer on an iPhone.)" when offline before the reader has been downloaded.
- **A check already waiting:** if the check bar is already showing, the photo isn't read: "Answer the check above first (Add or Skip), then try the photo again." If one appears while the photo is being read: "Read <LPN> from the printed label, but another check is waiting above. Answer it, then try the photo again."
- With **photos** switched off in the site settings, an uploaded photo with no barcode just says "No barcode found. Try a clearer, closer photo of the barcode."
- The problem report gets a `scan` entry starting "Printed LPN read:" (build 64: "Upload photo:"; build 63: "Scan by photo:") listing the LPNs read from the label (or "none") and how many other numbers were read.

**Several photos (Upload photo, build 65).** Choosing more than one photo reads them one after another:

- Every line under the camera box, and the question in the check bar, starts "Photo n of m: ", for example "Photo 2 of 5: Reading barcode…" or "Photo 3 of 5: Read <LPN> from the printed label (no barcode found): check it matches the label. Add it as <type>?"
- When a photo needs an answer (the printed LPN, a warning, or "Ask me to confirm each scanned barcode"), the next photo waits until **Add** or **Skip** is tapped. If a check from something else (for example a handheld scan) is already showing, the photos wait for it to be answered first; a photo whose reading finished while such a check was open is read again afterwards and then offered.
- While photos are being read, **Live scan**, **Scan by photo** and **Upload photo** don't start anything; they say "Still reading your photos. Answer the check above (Add or Skip) to go on to the next one." (when a check is waiting) or "Still reading your photos. Wait for them to finish before choosing more."
- At the end a summary says what happened, for example "5 photos read: 3 pallets added, 1 skipped, nothing found on 1 photo." ("no pallets added" or "1 pallet added" as needed; the skipped and nothing-found parts only when there are any). Notes that would otherwise be lost follow it: "Photo 2: a number after “LPN:” was read without its letters (<digits>): type it in with the letters at the start." and "Photo 4: couldn’t be read: <reason>." Only pallets from the photos are counted, not ones scanned or typed meanwhile. It shows under the camera box, or in the message line under the buttons if the camera box has closed.
- **What stops it:** **Stop scanning**, **Clear all**, **Start new delivery** (only once it really starts a new one, not the first press that only asks you to export first), opening or exporting a saved delivery, and unticking "Warn me about duplicate or unusual LPNs before adding them" in Settings. A question from the photos is taken away, but one from a handheld scan stays for an answer. A photo still being read when it stopped adds nothing and asks nothing, so no photo goes into the wrong delivery.
- Choosing one photo works as before, with no "Photo 1 of 1" and no summary.

On phones the four buttons share one row and stay at least 48px tall; labels can wrap onto two lines (line height 1.15, smaller side padding since build 64), and under 360px wide the gaps, padding and text are a little smaller still. Under 300px the row wraps. Since build 65 the camera box's own buttons (**Read the printed LPN**, **Torch**, **Stop scanning**) also wrap onto more lines, lined up on the right, on small phones and with big text, and the message beside them keeps at least 200px.

**Test a handheld scanner (build 59).** A section in Settings, after **Date format** and before **Share this app**: "Tap the box and scan any barcode with your handheld or Bluetooth scanner. Nothing is added to the log." The box is labelled **Scan a barcode here**. Nothing scanned into it is logged, and the box empties after each result, so the next barcode can be scanned straight away. It has no site switch, so it is always shown. The result line starts "Read “<code>” (<n> characters, in <m> ms)." (no time for a single character; the time runs from the first to the last character), then says what came after the code:

- **Enter:** "Enter was sent after it, so a scan into the LPN box logs the pallet straight away."
- **Tab:** "Tab was sent after it instead of Enter, so a scan into the LPN box would move to the next box without logging the pallet. Set the scanner to send Enter after each scan (often called a suffix or CR) using the setup barcodes in its manual." The cursor stays in the test box.
- **Nothing:** when no key comes for 1.5 seconds after the last character, "Nothing was sent after it, so you’d need to tap Add after each scan." and the same advice to set the scanner to send Enter. (Waiting 1.5 seconds means slow typing isn't cut off.)
- **Only Enter** with an empty box: "Only Enter came through. Scan a barcode with the box selected."

- No problem: "It looks like an LPN."

When there are several, they are joined with ", and "; a prefix problem is not mentioned alongside them.

## Undo for the last 10 changes (build 62)

Every change that offers Undo (removing a pallet with ✕ or ↶, an edit of a pallet, Clear all, Clear trailer, seals and notes, and Start new delivery) is kept in a list of the last 10, newest first. Older ones drop off. The list is only kept while the app is open: reloading the app forgets it.

- **The Undo bar** shows the newest, for example "Removed VLT000000003 (1 earlier)". Its **Undo** undoes that one, and the bar then shows the next.
- **The Undo button next to Export** shows while there is anything to undo, also after the bar has gone. It undoes the newest change each time. Screen readers hear, for example, "Undo: Removed VLT000000001 (2 earlier changes can be undone after it)". On phones it sits above Export, with **Clear all** below them at the bottom; on wider screens it is just left of Export, with Clear all on the left.
- **Ctrl+Z** (Cmd+Z on a Mac) undoes the newest change, but not while the cursor is in a box (there it undoes the typing, as usual), and not while the Guide, Settings, Saved deliveries, the install box or the report box is open over the log.
- **What was undone** is said in the status line under the log, for example "Undone: Removed VLT000000003. 1 more can be undone."
- **Keyboard focus:** when the last undo hides the bar and the Undo button while one of them had focus, focus moves to **Export**.
- **Whole-log changes:** **Clear all**, **Start new delivery** and **Clear trailer, seals and notes** can only be undone while the log and the delivery details are exactly as they were straight after the change. Once a pallet has been logged, or a box such as the trailer number has been changed, Undo says, for example, "“Cleared 1 pallet” can’t be undone now, because the log has changed since, and nor can the 1 earlier change." and the whole list is forgotten, because putting back the old log would lose the new work, and the older changes belonged to the old log. Other changes (a removed pallet, an edit) are undone whenever they are reached.
- **Forgotten on purpose:** opening a saved delivery, and restoring a backup, forget the whole list, since undoing would then change the wrong delivery or write old data over the restored backup.
- Nothing is undone while a saved delivery is being exported from Saved deliveries.
- Clear all now says "Cleared 1 pallet" for one (it said "Cleared 1 pallets" before build 62).

Deleting a saved delivery in Saved deliveries has its own "Deleted. Undo" in the list, as before; it isn't part of this list.

## Manifest check

The section opens (tap **Manifest check**) on **Manifest date**, then the two steps side by side: **1. LPN log** and **2. Manifest photos or PDFs** ("2. Manifest PDFs" when photo reading is switched off in the site settings, build 53). Below them is the closed **Prefix presets** section; its heading shows the current choice in brackets, for example "(all prefixes)", the preset name, or the typed prefix list. The **Manifest check** heading button and **Show missing** are at least 44px tall.

On phones, while the Manifest check is open and its top is in the upper part of the screen (above 45% of the screen height), the pallet entry bar slides down out of view so it does not cover the section. It slides back when you scroll up towards the log, and it never slides away while you are typing or scanning into it.

- **Manifest sources:** photos (OCR), PDFs (text read exactly, scanned pages by OCR, several at once), or typed/pasted numbers. The PDF reader is downloaded the first time a PDF is read, so that needs internet once; after that PDFs can be read offline.
- **Log sources:** Use current log, a saved delivery, an exported `.xlsx`/`.csv`/`.xls`, an app-made PDF (read exactly), another PDF, or a photo of a printed log.
- **Use n as expected:** while a manifest is loaded and Expected pallets is empty, the progress line offers to copy the manifest count into Expected pallets.
- **How photos are read (build 35):** each photo is made black and white by comparing every point with the paper around it, so shade across the page and paper grain don't turn into junk, and pages with ruled lines are read in full. The numbers on one photo are then matched to each other: when most of a page's numbers are, say, `VLT` + 9 digits, a reading such as `VL1004040355` is put back to `VLT004040355`, and an O read as an extra 0 after the prefix (`RUN0001832816` where the others are `RUN001832…`) is dropped. A number with nothing to compare against is kept as read. Since build 36, specks on the paper that read as a code are left out: when a photo's numbers show a clear pattern, a reading with a prefix seen nowhere else on that photo and without an LPN's digit count (9 or 10, or 10 or 11 for `IM`; for example `DFA51400180` on a page of `VLT` numbers) is not added, and the problem log notes it as "Ignored as not looking like this page's LPNs". A short reading of a prefix the page uses is still added so you can check it. Since build 37, a reading whose prefix has a different number of letters from every prefix on the photo (for example `CO1080002090` or `L1121100001` among `VLT` numbers) is left out too. A number with another prefix of the same length and 9 or 10 digits is still added. `IM` numbers (full pallet picks, two letters) are always kept, whatever the other numbers look like. When the most common number shape on a photo is a tie (for example 9 and 10 digits), the plainly printed readings decide it.
- **Prefix presets** (tap the heading to open) limit which numbers OCR picks up. Since build 53, when photo reading is switched off in the site settings, the presets are hidden and any saved prefix list is ignored, so PDFs give every number. The list is applied after the tidy-up above, so a mended number with a listed prefix is kept. Leave the list empty for any 1–3 letter prefix. Presets come from `presets.json` and from presets saved on the device.
- **What each file added:** after reading manifest photos, manifest PDFs or log photos, the message has one note per file, for example "Photo 1: found 2 LPNs, 1 new, 1 already in the list." (PDFs are named by their file name, log photos as "Log photo n"). A file where nothing was found says "No LPNs could be read: try a closer, sharper photo in good light." or, for a PDF, "No LPNs could be read from this PDF."
- **Numbers left out by the prefix list:** when a prefix list is set, numbers of 1–3 letters followed by an LPN's digit count (exactly 9 or 10 real digits, or 10 or 11 after `IM`; since build 40 also an `IM` number with 9 digits, one short and probably a misread) whose letters aren't in the list are not added, but the note names them (up to four, then "…"), for example "2 other numbers (QUB001899186, QUB001899210) start with QUB, which isn’t in the prefix list. If they are LPNs, add QUB under Prefix presets (or clear the prefixes) and read the photo again." For PDFs it says "read the PDF again". Numbers of other lengths (PO, phone or reference numbers, such as `TEL 01234567890`) are never named. With an empty prefix list nothing is left out.
- **Readings that didn't look like the page (build 37):** readings left out by the tidy-up that have an LPN's digit count (9 or 10, or 10 or 11 for `IM`) are named in the photo's note, for example "3 other readings (CO1080002090, RR1004040021, L1121100001) didn’t look like the other LPNs on this page, so they were left out. If one is a real LPN, type it in the box." They are not added; type in any that are real.
- **Numbers corrected to match the page (build 45):** when the tidy-up changes a reading to match the other numbers on the photo (for example `VL1004040355` to `VLT004040355`, or an extra 0 dropped), and the corrected number is added, the photo's note names it so it can be checked. Since build 59 it reads "1 number looked misread, so it was corrected (VLT004040355): check it against the paper." (or "n numbers looked misread, so they were corrected (…): check them against the paper.", up to four named, then "…"); before build 59 it said "corrected to match the others on the page", which was wrong for a page with one LPN, where nothing is matched to other numbers. A number read twice and corrected is named once. The problem log adds "corrected to match the page" with the numbers.
- **Single-letter prefixes, numbers read with a gap and pages with one LPN (build 57, from problem report #2):** an LPN that starts with a single `V`, `R` or `Q` (for example `V0013323651` on a page of `VLT` numbers) is now kept when it has an LPN's digit count (9 or 10) and was printed straight after an "LPN:" label; before, its one-letter prefix among three-letter ones got it left out. Without the label in front, or with the wrong number of digits (`V12345`, or a speck read as `R014908200`), it is still left out. A number read with a gap in it straight after an "LPN:" label (`QUB00191 1625`) is joined into one LPN (`QUB001911625`) when the two parts sit on the same line close together and together have an LPN's digit count; digits further along the line, on the next line or without a label in front are never joined on. The word "LPN" is never taken as a prefix (`LPN 0013323651` doesn't become an LPN). On a photo with nothing to compare with (one LPN on it, for example), a close-up reading that only adds a 0 straight after the prefix to a number read plainly (`RUN0001840861` for a printed `RUN001840861`) is not used: the plain reading is kept and named for checking with the usual corrected-number sentence ("1 number looked misread, so it was corrected (RUN001840861): check it against the paper." since build 59). On such a page, a reading without an "LPN:" label whose prefix differs from the labelled ones (print showing through from the back of the page, such as `FI8111010009`) is left out and, with an LPN's digit count, named as "didn’t look like the other LPNs on this page"; a `V`, `R` or `Q` number with an LPN's digit count is never left out this way.
- **A number read without its letters (build 57):** when the reader sees 9 or 10 digits straight after an "LPN:" label but not the letters before them (the `V` of `V0013323651`), the number is not added, but the photo's note names it: "A number after “LPN:” (0013323651) was read without its letters: check the paper and type it in with the letters at the start." ("n numbers after “LPN:” (…) were read without their letters: … type them in …" for more, up to four named, then "…"). It comes after the corrected-number sentence and before the "didn’t look like" one. A photo with only such numbers counts as having found something, so it isn't turned and read again. The problem log records "Read after LPN: without its letters: <digits>".
- **Report a problem with these photos (build 45):** after a batch of manifest photos is read, a **Report a problem with these photos** link appears under the message. It opens the report box (see [Report a problem or idea](#report-a-problem-or-idea)) set to **Problem**, with the photo that read worst already attached (made smaller as usual): a photo that couldn't be read first, then the one with the fewest LPNs found, then the one with the most numbers skipped by the prefix list, left out or corrected. The text box stays empty; its hint asks "What went wrong with photo n? For example, which numbers were missing or wrong.", so the report always has your own words. While the photo is being added the note says "Adding photo n…" and **Send** is greyed out; then it says "Photo n attached (n KB)". If the photo can't be added, the box says so and the report can still be sent. The photos are only held in memory for this, never saved; **Clear** and reading manifest PDFs remove the link and forget them, and so does choosing a new batch.
- **Sideways and upside-down photos (builds 46 and 47):** when a manifest photo gives nothing that looks like an LPN (no LPNs, nothing left out by the prefix list and no readings that didn't look like the page), it is turned 90° and read again, and if that also finds nothing, turned 270° and read again. Since build 47, if neither sideways turn finds anything, it is turned 180° (upside down) and read once more. While this happens the message shows "Photo n of n: No numbers found, so turning the photo to try again…". When a turned reading finds something, the photo's note ends "The photo was sideways, so it was turned to read it." (90° or 270°) or "The photo was upside down, so it was turned to read it." (180°). If no way up finds anything, the usual "No LPNs could be read…" note shows; a blank or blurry photo is therefore read four times before that note, so it takes longer than an upright one. A photo that only has numbers with an unlisted prefix counts as found, so it is not turned. Log photos and scanned PDF pages go through the same reader and are turned the same way, but only manifest photos show the "turning the photo" message. After each photo the app frees the memory of its full-size copies straight away (phones, Safari above all, give it back late otherwise).
- **Add a prefix with one tap (build 46):** when manifest photos or manifest PDFs give numbers that were left out because their prefix isn't in the prefix list, the note says "…tap Add RBY below to add them to the prefix list." (instead of "add RBY under Prefix presets … and read the photo again"), and a button **Add RBY to the prefix list** appears under the message, one per missing prefix. Tapping it adds the prefix to the prefix list (saved as usual) and adds the numbers already read with that prefix to the manifest box, without reading the photos again. The message then says "Added RBY to the prefix list and n numbers starting with RBY to the manifest list (n already there). Check them against the paper copy." followed by the earlier per-photo notes (with the "tap Add" sentence removed). If Check results is open, the results are worked out again. The button goes, and keyboard focus moves to the next Add button or, if none is left, the manifest numbers box. The buttons only show while a prefix list is set; they go when the prefix list is changed to include that prefix, or cleared, and with **Clear** or a new batch of photos or PDFs. Log photos don't get the button.
- **One bad file doesn't stop the rest:** if a manifest photo or log photo can't be read, its note says "Photo n: couldn’t be read (reason)." and the next photos are still read. Manifest PDFs already worked this way; a PDF that fails is listed under "Couldn’t read:". The exception is the PDF reader failing to load, which stops at that file with the "PDF reader couldn’t load" message.
- **Unusual digit counts:** after reading or typing manifest or log numbers, the message ends with "These have an unusual number of digits, so check them against the paper copy: …" (up to eight, then "and n more") for lines that are letters followed by digits but not 9 or 10 digits (10 or 11 for `IM`). Since build 39 `IM` numbers with 10 or 11 digits are not listed there; a 9-digit `IM` number is. Lines in another form, such as `VLT-004040265` or `004040265`, are judged only by the digits at the end (9 or 10 is fine), as before build 39; build 39 had listed them all, and build 40 put this back.
- A note under the manifest numbers box reminds you that numbers read from photos can be misread, so check them first. (This replaced the earlier "still being tested" warning at the top of the section.)
- **Check results** lists Missing (on the manifest, not logged: report), Log only (logged, not on the manifest: book in) and Matched. **Fix** corrects a misread number, ✕ removes it.
- **Refused pallets (build 62)** are matched like any other pallet (they came off the trailer). The copy of the log in the Manifest check export, when made from the current log, a saved delivery or an app-made PDF log, leaves them out of its Total and adds a "Refused (not in total)" row, the same as the log's own export; a log uploaded as a spreadsheet is copied as it is.
- **Pallets with no LPN (build 55):** "No LPN n" lines in the log can't be matched, so they are left out of Missing, Log only and Matched and counted on their own: the summary adds "No LPN (check by hand): n", the Excel export adds a "No LPN pallets" row to its summary box and "No LPN: n" to its title line, the PDF adds a "No LPN pallets" row to its Summary table, and the shared list ends "Pallets with no LPN (check by hand): n". These lines only appear when there are any. They aren't listed as an unusual number of digits, and a log with only No LPN pallets can still be checked. An uploaded log says, for example, "log.xlsx: 12 LPNs found and 1 with no LPN"; **Use current log** and a saved delivery now say "n pallets" (they said "n LPNs").
- **Share missing list (build 49):** a button at the top of the results. On a phone it opens the share menu (WhatsApp, Teams, email, text…) with a short message:

  ```
  Manifest check 01/11/2026, trailer TR4471
  Missing from the log (2): RBY006292169, RBY006292211
  On the log only, to book in (1): QUB001899182
  Matched: 2 of 4 on the manifest
  ```

  The date and trailer parts are left out when they aren't known, and an empty list says "none". Closing the share menu without sending does nothing. Where there is no share menu (most computers), or sharing fails, the text is copied and the message under the buttons says "The missing list was copied. Paste it into a message or email." If copying isn't allowed either, the message shows the list itself ("Sharing isn’t available here. The list is: …").
- **Export** gives the comparison as Excel (`Manifest-check-<date>-<trailer>.xlsx`), Email PDF or Print (`Manifest-check-<date>-<trailer>.pdf`). Since build 46 the trailer part is the trailer number of the delivery that was checked: the current log's trailer box when **Use current log** loaded it, or the saved delivery's trailer when a saved delivery was chosen. A log uploaded as a file or read from a photo gives no trailer part, and neither does a delivery without a trailer number. When the comparison is added to an uploaded `.xlsx` log, the file keeps the log's own name with " (with manifest check)". With "Include a copy of the log" on, an uploaded `.xlsx` log gets the comparison as a new tab, and PDFs get the log appended. When a log PDF is appended, any links and page-open actions in it are removed; the printed pages are unchanged. Values from an uploaded log are only ever written as plain text or numbers, so a file from outside can't add formulas or links to the export.
- **Photo reader:** reading photos downloads the photo reader and its language data the first time, which can take a while on a weak signal. If it hasn't started after 90 seconds, or can't be downloaded, it stops with "The photo reader couldn’t load…" and the next try downloads it again. Since build 41 one reader is started for a batch of photos (or scanned PDF pages) and reused, so the second and later photos start faster; it is closed 15 seconds after the last photo to free memory. If one photo takes longer than 2 minutes to read (for example the phone stopped the reader while the app was in the background), that photo fails with "The photo reader stopped. Try the photo again." and the next photo gets a fresh reader. Reading manifest photos and a log photo at the same time is fine: they take turns. Reading photos needs iOS 16 or newer on an iPhone; older phones can still scan barcodes, read PDFs (iOS 16.4+) and type numbers.

**Trailer number in file names (build 46).** The `-<trailer>` part is the Trailer number box, for example `LPN-log-2026-11-01-TR4471.xlsx`. Anything other than letters, numbers and dashes becomes a dash, repeated dashes become one, dashes at the start and end are dropped, and it is cut to 20 characters (`TR 4471/A` gives `-TR-4471-A`). With no trailer number the name is `LPN-log-<yyyy-mm-dd>.xlsx` as before. Exports from Saved deliveries use that delivery's trailer number. With no date the date part is `no-date`.

**Site or store name in the title (build 62).** **Settings → Site or store name** (under Text size, placeholder "Optional, for example 323 Wigan", up to 40 characters; the note says "Added to the title of every export, so logs from different sites are easy to tell apart."). When set, it is added after the title of every export, for example "Goods-in pallet log – 323 Wigan" and "Manifest check – 323 Wigan": the Excel log, the basic `.xls`, the PDF (Email PDF and Print), exports from Saved deliveries, and the Manifest check's Excel and PDF. Runs of spaces become one and the ends are trimmed when it is saved. A long title gets a smaller font so it isn't cut off: on the Excel sheets titles over 34 characters shrink from 22pt (down to 13pt at the least), and on PDFs the font goes down from 18pt until the title fits between the margins (down to 11pt). Left blank (the default), the titles are as before. The name isn't in the file names. It is saved on the phone with the other settings (and in backups).

**Refused pallets on exports (build 62).** See [Refused pallets](#refused-pallets-build-62): left out of **Total**, counted in a "Refused (not in total)" row, and listed in Delivery Details as "Refused pallet | <LPN>: sent back with the driver". In the Excel log the Pallet Type box's thick border closes under the Refused row, and the Delivery Details box moves down one row.

If an expected count is set and differs from the total, the first export attempt shows a reminder instead; choosing it again proceeds.

**Long LPNs and notes in the spreadsheets.** On the pallet log and the manifest check sheet, the LPN column widens to fit the longest LPN in the file (it never gets narrower than the usual width, and stops at 40 characters wide). A value too long even for that, such as a web address scanned by mistake, wraps onto a taller row instead of stretching the column. Rows in the Delivery Details table grow tall enough to show long notes in full. The logo above the table is sized to the width of the table.

**Which version made the file.** Every export says which version of the app made it, for example "LPN Pallet Log v4.0 (build 52)". The version is the newest entry in the Changelog (its first heading, `v4.0` since build 52; `v3.30` before); the build is the cache number in `sw.js` (`lpn-log-v52` is build 52).

| Export | Where the version appears |
|---|---|
| Excel log and manifest check sheet | A small grey line under the tables: "Made with LPN Pallet Log v4.0 (build 52) on dd/mm/yyyy at hh:mm." (the date follows the Date format setting), and the left side of the printed page footer |
| PDF (Email PDF, Print, saved deliveries) | The left side of the page footer |
| Basic `.xls` (when the spreadsheet builder can't load) | A "Made with … on … at hh:mm." line under the table |

If the build number can't be found within 1.5 seconds (for example on a very weak signal), the export goes ahead without it and shows only "LPN Pallet Log v4.0".

Importing an exported log (Saved deliveries or the Manifest check) stops reading LPNs at the "Made with" line, so it is never taken for a pallet, even if someone has deleted the blank row above it. Both read spreadsheets the same way, so a log gives the same pallets in either place.

After a log export (Excel, Email PDF or Print) the log shows "Exported at hh:mm". If pallets are changed afterwards it reads "Changed since it was exported at hh:mm" in amber, and Start new delivery will ask for a fresh export first. Exports made from Saved deliveries don't change this note.

## Backup and restore

Everything (the current log, saved deliveries, names, presets, logo and settings) is stored in this browser only.

**Back up:** **Settings → Backup → Download backup**, or **Back up now** in Saved deliveries. This saves `lpn-backup-<yyyy-mm-dd>.json`.

**Restore** (for example on a new phone):

1. **Settings → Backup → Restore backup**, then choose the `.json` file.
2. The app checks the file and says what it holds, for example "This backup has a log of 12 pallets and 4 saved deliveries." Nothing has changed yet. A file that isn't a backup from this app, or is damaged, is refused here.
3. Tap **Replace my data with this backup**, or **Cancel** to leave everything as it is.
4. A copy of your current data downloads first (`lpn-backup-<date>.json`). On iPhone, confirm the download if asked. If the copy can't be saved, the restore stops and nothing is replaced.
5. The message says "Backup restored. Make sure the copy of your previous data has saved, then reload the app…". Check the copy has saved, then tap **Reload the app**. The app doesn't reload by itself. Since build 62 a restore forgets the undo list at once, so an Undo before the reload can't write the old data over the restored backup.

While checking, the app tidies the backup: anything it doesn't recognise is left out (for example an unknown pallet type becomes Mixed, and a logo that isn't a PNG or JPEG image is dropped). The same tidying happens every time the app starts, so damaged saved data can't stop it opening.

The problem log (see [Problem report](#problem-report)) is never put in a backup, is ignored if a backup file contains one, and is left as it was when a backup is restored.

## Report a problem or idea

Since build 44 the form is a box in the middle of the screen. Open it with the **Report a problem** button (speech-bubble icon) at the top of the page: at the right of the title row on phones, just before **Guide** on desktop. Since build 58 the button says **Report a problem** (it said just **Report** before), so it's clear it is for problems with the app or ideas for it; screen readers still hear "Report a problem or idea". The cursor goes into the text box. **Close**, **Escape** or tapping outside the box closes it and puts you back where you were (in the Guide or Settings if you came from there).

1. Choose **Problem** or **Idea**.
2. Type what happened or what would help (up to 4000 characters).
3. Optional (build 50): **Your name (optional)**, up to 60 characters, so Jamie knows who to ask. Runs of spaces become one and the ends are trimmed. The name is remembered on this phone and filled in the next time the box opens; clearing the box and sending forgets it. Left empty, no name is sent.

6. Tap **Send**. "Sent. Thank you!" means it has arrived; the box closes by itself 1.5 seconds later.

Since build 50, **Send**, **Close** and the status line under them are pinned to the bottom of the box, so they stay on screen however tall the form gets (Extra large text, the name box, a short phone or the keyboard open); the form scrolls above them. On screens no taller than 700px the text box is a little shorter (at least 76px).

Reports go to Jamie's private GitHub repository through a Cloudflare server. A name, when given, shows in the issue under "From:" as plain text. Settings' **Report a problem or idea** section points to the Guide's **Your data and privacy** section for what a report includes (see [Your data and privacy](#your-data-and-privacy-build-50)). Use Download problem report below and send the file to Jamie instead." (see [installation](installation.md#feedback-worker-report-a-problem-or-idea)).

**No signal.** If the phone is offline, or the server is busy, the report is kept on the phone and sent when it is back online (when the browser reports it is online, and 4 seconds after the app opens). When the box opens with reports waiting, it says how many ("2 reports are waiting to be sent when you’re back online."). A report the server refuses (for example too long) shows the server's reason and is not kept. Waiting reports belong to the phone: they are never put in a backup or taken from one.

## Problem report

**Settings → Problem report** has **Download problem report** and **Clear**.

The app keeps a short log of what it has done on this device: the last 300 events, each cut to 300 characters. It records manifest photo, manifest PDF and log photo reads, the LPNs read from a label's printed text by **Upload photo** or **Read the printed LPN** (build 65; entries start "Printed LPN read:"; **Upload photo** only in build 64, **Scan by photo** in build 63) (file type and size, how many LPNs were found, added and already listed, numbers left out by the prefix list, readings left out as not looking like the page's LPNs, failures), what the photo reader and PDF reader got from each file (word or page count, LPNs found and the first 150 characters of the text read from a photo), backup restores, and script errors (including failed promises). It is only sent if you attach it to a report from **Report a problem or idea**; nothing is sent by itself.

**Download problem report** saves a plain text file, `lpn-problem-report-<yyyy-mm-dd>.txt`, with:

- when it was made, the app version and build, the browser (user agent), screen and window size and pixel ratio, whether it runs as an installed app, whether it is online and whether the service worker is active;
- the current state: pallets in the log, delivery date, expected pallets, the Manifest check prefixes, the manifest numbers and log numbers in the Manifest check boxes, and the Manifest check message;
- the recent events, oldest first, each with its time and kind (`manifest`, `pdf`, `ocr`, `backup`, `error`).

The message then says "Problem report downloaded. Send it along with what happened." **Clear** empties the problem log ("Problem log cleared.").

Section 9 of the Guide says: "Something not working, or an idea?" with a **Report a problem or idea** link (since build 42; before, it told staff to download the problem report and send it). The report contains LPNs, file names and text read from photos, so treat it like a delivery record.

## Your data and privacy (build 50)

Section 10 of the Guide, **Your data and privacy** ("Privacy" in the contents bar), says in plain words:

- "Photos and PDFs you scan or add are read on the phone and aren’t saved. Only a short note of what was read goes in the problem log on this phone." (since build 64; before, "Manifest photos and PDFs are read…"). (since build 58; it said "no Report button" before), and the line about manifest photos and PDFs is left out when the Manifest check is switched off.
- Clearing the site's data in the browser deletes the log and saved deliveries. On an iPhone, a web page not added to the home screen can be cleared after a few weeks unused, so install the app and use **Back up now**.
