# Testing

## Run the checks

```bash
npm install
npx playwright install chromium   # once
npm test
```

`npm install` fetches Playwright and the seven libraries the app loads from CDNs, at the same exact versions (`package.json` `devDependencies`): `exceljs` 4.4.0, `jspdf` 2.5.1, `jspdf-autotable` 3.8.2, `pdfjs-dist` 6.4.299 and `pdf-lib` 1.17.1, which the checks use for real (see [Real export libraries](#real-export-libraries) below), plus `tesseract.js` 5.1.1 and `@zxing/library` 0.21.3, which are only there so the version check and the advisory check cover them. The app itself never loads anything from `node_modules`.

`npm test` runs `node tests/run.js`. It starts its own static server on a random local port, so nothing else needs to be running. Output is one line per check and a final `N passed, N failed`; the exit code is non-zero on any failure.

On GitHub, `.github/workflows/test.yml` (workflow name **Checks**) runs the same command on every push and pull request (Node 22, Chromium), with `npm install --ignore-scripts` so no package install scripts run, read-only repository access (`permissions: contents: read`) and a 20-minute limit (`timeout-minutes: 20`; it was 10 until a slow Playwright browser install on GitHub made build 44's Checks run hit the limit and be cancelled; on `main` since build 45's release). Results appear in the **Actions** tab, and failed checks are shown as annotations on the run.

### Real export libraries

When all six library files are in `node_modules` (`exceljs.min.js`, `jspdf.umd.min.js`, `jspdf.plugin.autotable.min.js`, `pdf-lib.min.js`, and pdf.js's `pdf.min.mjs` and `pdf.worker.min.mjs`, taken from `pdfjs-dist/legacy/build/`), the "Real export libraries" group runs. Otherwise it prints "skipped here" and carries on; this happens where npm cannot download packages, such as the Claude cloud sandbox. Locally without the libraries the run has 248 checks at build 51 (one more than build 50; the new check runs on GitHub too); build 50 had 247, and 272 on GitHub with them (233 and 258 at build 49; 220 and 245 at build 48; 213 and 238 at build 47; 212 at build 46; 181 at build 42, when it had 206 with them; with them is always the case on GitHub).

On GitHub (`GITHUB_ACTIONS` set) two extra lines are printed at the end:

- if the libraries are missing, an `::error` annotation "Real export libraries missing" is added and the run counts as failed, so the real checks can't be skipped there unnoticed;
- always, a `::notice` annotation titled **Checks** with the totals, for example "164 passed, 0 failed, including the real export library checks" (or "real export library checks skipped").

Because run logs can't be downloaded from a Claude cloud session, the notice is the way to read the result there: find the job id of the run, then

```bash
gh api repos/Jamie9904/Jamie9904.github.io/check-runs/<job id>/annotations
```

### Before a push (Claude Code hook)

When Claude Code runs a real `git push` (not, for example, `git stash push`) from this repository, the `PreToolUse` hook `.claude/hooks/lpn_git_guard.py` runs `node tests/run.js` first (with `NODE_PATH` pointed at the global npm modules) and stops the push if any check fails, showing the failing lines. A push of only the `docs` branch skips the checks, because it does not change the site. If the checks take longer than 280 seconds, the push is stopped too. This only applies to pushes made through Claude Code; a plain `git push` from a terminal is not checked locally, but `test.yml` still runs on GitHub.

## Security advisories and library fingerprints

Two more scripts need internet, so they are not part of `npm test`:

```bash
node tests/advisories.js     # security advisories for the seven pinned libraries
node tests/sri.js            # library files still match their fingerprints
```

**`tests/advisories.js`** reads the seven versions from `package.json` and asks the OSV database (`https://api.osv.dev/v1/query`, npm ecosystem) about each one. For every advisory found:

- listed in `tests/advisories-accepted.json` (by its id or any alias): printed as a `note` with the written reason;
- otherwise HIGH or CRITICAL: an error ("New security advisory");
- otherwise: a warning.

It also adds a notice when an accepted entry is no longer reported for that version ("can be removed from tests/advisories-accepted.json"). It ends with a summary such as "0 new serious, 0 new other, 12 accepted", and exits with 1 if there is a new serious advisory, a library is missing from `package.json`, or a lookup failed. On GitHub the lines are annotations (`::error`, `::warning`, `::notice`). Without internet it can be tried against saved answers: `node tests/advisories.js --from saved-osv-answers.json`, where the file maps `name@version` to OSV's list of advisories.

`tests/advisories-accepted.json` currently lists 12 jsPDF 2.5.1 advisories, each with the reason it doesn't affect the app (for example "addJS: the app doesn't use addJS."). Its `_about` note lists what the app does use jsPDF for. Keep the reasons true when the export code changes, and remove entries once a library is upgraded past them.

**`tests/sri.js`** reads every address and `sha384` hash from the `SRI` map in `core.js`, downloads each file, and compares the hash. It prints `ok` or `FAIL` per file and "n of n library files match", and exits with 1 if any file has changed, failed to download, or no hashes were found.

Both run in `health.yml` (a failure fails the weekly run) and in `test.yml` with `continue-on-error: true` (shown on the run but never blocking a push).

## Demo video screen fingerprint

`tools/demo-video/screens.json` records what the key screens looked like when the Guide demo video was last recorded. `tools/demo-video/screens.js` makes it: it seeds `localStorage` with the same made-up delivery the video uses (eight pallets, date 30/10/2026, trailer TR4471, received by Jamie, 12 expected), fixes the page clock to that day (`page.clock.setFixedTime(new Date("2026-10-30T12:00:00"))`, so the "log is dated before today" reminder never appears and moves the screen on later days), opens the app at 390×844 and records, for each part, its position, size, text (first 80 characters) and background and text colours:

- log view: `header h1`, `#btnGuide`, `#delSum` (folded), `#sum`, `#tyb`, `#lpn` and `#expBtn`;
- manifest check: `#cmpSum` and `#cmpRes`, after checking a nine-number manifest against the log (their vertical position is left out, because it depends on scrolling).

`make.sh` rewrites `screens.json` after each re-recording (`node screens.js --write`, which serves the repository locally with Playwright and blocks all outside requests). In `npm test`, the "Demo video" group checks that the file exists, takes the same fingerprint of the current app and lists the differences: a part that is gone or new, changed text, changed colours, or a move or resize of more than 6px. The result is printed as a `note` line ("still matches", or the first six differences with a reminder to re-record with `sh tools/demo-video/make.sh`). On GitHub a difference also adds a **Demo video may be out of date** warning annotation. A difference never fails the run.

Since build 41 the note lists `#btnGuide` as moved and resized slightly, because the header buttons now size to their text (`flex:1 1 auto` at up to 620px wide). The video was not re-recorded for that, so the warning is expected until the next recording.

## Weekly health check

`.github/workflows/health.yml` runs every Monday at 07:36 UTC (`cron: "36 7 * * 1"`) and can be started by hand from **Actions → Weekly health check → Run workflow**. It checks out `main` and runs these steps:

1. **Live site is up and on the latest version.** Fetches `https://jamie9904.github.io/` (with a cache-busting `?health=` query), checks the page title is `LPN Pallet Log`, then fetches the live `sw.js` and compares its `lpn-log-vN` cache name with the one in `sw.js` on `main`. A mismatch means the last update has not been published.
2. **CDN libraries still download.** Collects every `cdnjs.cloudflare.com`, `cdn.jsdelivr.net` and `unpkg.com` URL written in the root `*.js` files and downloads each one. The pdf.js worker addresses are written out in full in `PDFJS_SRC`, so they are checked like any other URL. Any failed download is reported as an error annotation naming the URL.
3. **Guide demo video is on the live site and plays.** Downloads `https://jamie9904.github.io/media/demo.mp4` and `media/demo-poster.jpg` (each with `curl --retry 2`; a failed download is an error). Installs `ffmpeg` if `ffprobe` is missing, reads the duration and the first video and audio stream codecs with `ffprobe`, and decodes the whole file with `ffmpeg -f null` (a damaged file fails). The step fails unless the video is longer than 20 seconds, the video is `h264` and the audio is `aac`; when it passes it adds a **Demo video** notice with the duration and codecs.
4. **Report system works (feedback Worker and its GitHub token).** Since build 45's release. Takes the first `https://….workers.dev/report` address written in `panels.js` (`FEEDBACK_URL`) and sends it `OPTIONS` with `Origin: https://jamie9904.github.io`; anything but 204 is a **Report system** error ("The feedback Worker didn't answer (HTTP …)"). If no address is found this part is skipped. Then, with the repository secret `FEEDBACK_GITHUB_TOKEN` (the same token the deploy job copies to the Worker):
   - not set: a warning that the token can't be checked, and the step ends there;
   - `GET https://api.github.com/repos/Jamie9904/lpn-feedback` with that token not answering 200: an error saying the token doesn't work any more and reports are waiting on phones, with the fix (a new token as in `tools/feedback-worker/README.md` step 2, update `FEEDBACK_GITHUB_TOKEN`, run **Deploy feedback Worker**); the step fails straight away;
   - GitHub's `github-authentication-token-expiration` answer header less than 30 days away: an error giving the days left and the date, with the same fix;
   - otherwise a notice: "Worker answers; GitHub token works and runs out in N days (date)", or "… (no expiry date)" when GitHub sends no expiry header (the current token gives "no expiry date").
   
   Last, it finds the commit of the last successful **Deploy feedback Worker** run (`gh run list --workflow feedback-worker.yml --status success`) and, if `tools/feedback-worker` differs between that commit and `main`, adds a warning (not a failure) to run **Deploy feedback Worker**. For that `git diff`, the checkout now fetches the full history (`fetch-depth: 0`). The step fails if the Worker didn't answer, the token failed or it runs out within 30 days.
5. **Security advisories for the app's libraries.** `node tests/advisories.js` (see above).
6. **Library files still match their fingerprints.** `node tests/sri.js` (see above).
7. **Automatic checks.** `npm install --ignore-scripts`, Playwright Chromium, then `npm test`, the same as `test.yml` (so the real export library checks run here too).
8. **The live site reads the user's manifest photos.** `node tools/ocr-check/check.js --url=https://jamie9904.github.io/`: the live app's own photo reader (the `js` engine) reads the photos in `tools/ocr-check/photos/` and they are scored against `expected.json`. When it passes, a **Live photo reading** notice gives the `Total:` line (23 of 23 at the time of writing, with `rby-upside-down.jpg` since build 47; 21 of 21 at build 46 with `run-sideways.jpg`; 18 of 18 before); when it fails, a **Live photo reading** error lists the lines with "right" or "read" (cut at 600 characters) and the step fails.

It has read-only repository access and a 15-minute limit (`test.yml` has 20 minutes since build 45; it was 10). `tools/release/ship.sh` also starts this workflow by hand on `main` after every release and waits for it (see [installation.md](installation.md#publishing-with-the-release-script)).

If any step fails, GitHub sends its standard failed-workflow email (for scheduled runs, to the account that last changed the schedule in the workflow file); a passing run sends nothing. The workflow does not fix anything itself.

## Photo reading check (`tools/ocr-check`)

`tools/ocr-check/check.js` runs the app's photo reading on a folder of manifest photos and scores the LPNs against the ones printed on them. It is also a module that `tests/run.js` uses (`score`, `load`, `readJs`, `readCli`, `openApp`).

```bash
NODE_PATH=$(npm root -g) node tools/ocr-check/check.js [folder] [--engine=cli|js] [--prefix=VLT,QUB]
```

- **folder:** photos plus `expected.json` (`{"photo.jpg": ["LPN", …]}`); photos may sit in a `photos/` subfolder. The default is `tools/ocr-check` itself: `photos/` holds the user's four manifest photos (`qub.jpg`, `rby.jpg`, `run.jpg`, `vlt.jpg`, sent on 31 Oct 2026, address boxes cut off) and, since build 46, `run-sideways.jpg` (`run.jpg` turned on its side, to check that sideways photos are turned and read) and, since build 47, `rby-upside-down.jpg` (`rby.jpg` turned 180°); `expected.json` lists their 23 LPNs (2 `RBY`, 7 `QUB`, 6 `VLT`, 3 `RUN`, the same 3 `RUN` for the sideways copy and the same 2 `RBY` for the upside-down copy). Without `expected.json` it just lists what each photo gives. To add a photo, put it in `photos/` (with any address or names cut off, as the repository is public) and its LPNs in `expected.json`.
- **`--engine=cli`** (the default when the `tesseract` command is installed): the app's `prep()` in the page, then the Tesseract 5 command (mode 11, TSV, letters-and-digits whitelist), the app's `extractLpns()` and `cropScaled()` close-ups read again by the command (mode 7), then the app's `photoLpns()`. Since build 46 it follows the app's turn loop: when a photo gives nothing LPN-like, the app's `turnCanvas()` turns the `prep()` canvas 90°, then 270°, then (since build 47) 180°, and it is read again. Works offline.
- **`--engine=js`** (the default otherwise): the app's real `ocrLpns()` with tesseract.js, exactly as on a phone, with one retry. Needs `cdn.jsdelivr.net` and the tessdata download.
- **`--url=<address>`:** reads with the app at that address, for example the live site, instead of serving this folder. It always uses the `js` engine (the site's own `ocrLpns()`). Requests to other hosts are aborted except the photo reader's files, the service worker is blocked, `lpninstallshown` is set so the install prompt stays closed, and a `?check=<time>` query is added to the address so a cached page isn't used. The address is printed in the first line.
- **`--prefix`:** sets the prefix list. Only the expected LPNs with a listed prefix must be found; the others must be reported as left out for the prefix (`.skipped`), or they count as missing ("not reported as left out").

The app is served from the repository on a local port in headless Chromium with the service worker blocked; every outside request is aborted except, with the `js` engine, the photo reader's files. For each photo it prints the time and "n of n right" with any missing, extra and (with `cli`) ignored readings. The exit code is 1 when any expected LPN is missing, anything extra is found or a photo can't be read. `tools/` is not part of the site zip.

## Strategy

- **External requests are blocked.** Every request not to the local server is aborted, so runs are offline and repeatable.
- **Real libraries are served in place of the CDN.** A page opened with `page(browser, width, { real: true })` gets a router on the whole browser context: a request to any other host whose file name is one of the library files in the `LIBS` map (ExcelJS, jsPDF, jspdf-autotable, pdf.js and its worker, pdf-lib, Tesseract.js and ZXing) is answered from `node_modules` (whichever CDN, cdnjs, jsDelivr or unpkg, the app asks first; all are served as `text/javascript` with `Access-Control-Allow-Origin: *`, as the real CDNs send, because the app loads libraries with `crossorigin` and an integrity hash), and everything else is still aborted. The route is set on the context, and service workers are blocked for that context, so the pdf.js worker and any request the service worker would have made also reach the router.
- **Service worker on, when needed.** `{ sw: true }` keeps the service worker running and still routes at the context level, so the worker's own library requests can be answered by the test. `{ handle }` lets a check answer chosen addresses itself (for example a 503, or a fake library). `{ net: true }` lets the photo reader's own files (`tesseract` or `tessdata` in the address) through to the real internet; it is only used in the GitHub-only group.
- **Blocks by the security policy are listened for** in two places: a `securitypolicyviolation` listener added before the page loads, and the console of the page and of every worker (blocks inside workers don't reach the page's event).
- **Time is faked for the photo reader's 90-second limit** with Playwright's clock (`p.clock.install()` and `runFor()`), and `window.Tesseract` is replaced by a stand-in whose worker fails or never starts.
- **Versions are tied to the app.** The library-version check reads the CDN URLs from `export.js`, `compare.js` and `scan.js`, so updating a library in the app without updating `package.json` (or the other way round) fails the checks.
- **ExcelJS is replaced by a recording stand-in** that keeps every cell value, font, border, merge, image and print setting, so the sheet layout can be asserted without the real library.
- **jsPDF is replaced for one check** (the "Export version note" group) by a stand-in that accepts any call and records the footer text and the PDF keywords, so `buildLogPdf()` can be checked for the version note.
- **A PDF reader that can't load is simulated** by opening a page with `{ noSW: true }`: outside requests are aborted as usual, and the service worker is blocked too, because otherwise it would fetch pdf.js itself where there is internet and the check would pass or fail depending on the network.
- **A worksheet is faked for the spreadsheet import checks.** A small stand-in sheet behaves like ExcelJS for merged cells: every cell in a merged block reports the block's text, and only the top-left cell is its own `master`. `window.ExcelJS` and `window.loadExcel` are swapped for stand-ins that hand back this sheet, then put back afterwards.
- **Damaged saved data is planted before the page loads** with an `init` script that writes the `lpn*` keys, and backup files are given to `#bkFile` with `setInputFiles` or a `DataTransfer`. `saveOnly` is replaced so the safety copy is counted (or made to fail) instead of downloaded.
- **A crafted log PDF is faked** by swapping `window.pdfjsLib` and `window.loadPdfJs` for stand-ins that return a document whose keywords hold the `LPNLOG2:` data, then putting them back.
- **A slow network is simulated** by wrapping `fetch` before the page loads so every request for `sw.js` waits 15 seconds; this checks that exports don't wait for the build number.
- Tests drive the app through its own globals (`newDelivery()`, `openHelp()`, `parseExported()`…) where clicking would only add flakiness, and through real typing and clicks for the add flow.

## Not covered

- The real libraries where npm can't fetch them (the checks are skipped there; push a branch and read the **Checks** notice from GitHub instead).
- pdf-lib beyond the merge check, and how the real files look: the real-library checks read the files back, they don't look at fonts, colours or page breaks. Spot-check by exporting from the live site; files can be rendered with LibreOffice to inspect layout.
- The manifest PDF (`buildCmpPdf()`) with the real libraries, and what the print view looks like (the policy check only shows `printBuf()` runs with nothing blocked).
- Camera scanning and BarcodeDetector, and ZXing reading a real barcode: the checks only load ZXing and create its reader under the policy. How well the photo reader reads real photos: the automatic checks run Tesseract on one clear drawn LPN only, check `prep()` on a drawn shaded page without reading it, and check `tidyReads()` on readings recorded from real photos. The user's manifest photos (four, plus a sideways copy of one since build 46 and an upside-down copy of another since build 47) are read with the real tesseract.js only on GitHub (in `test.yml`, and with the live site in the weekly health check) and with `tools/ocr-check` by hand; nothing is checked on a real iPhone, and only those four photos from one site are covered.
- The security policy on browsers other than Chromium, including older Safari (where reading photos needs iOS 16+).
- That `lpn-libs-v1` is deleted when the new service worker activates (the offline store checks only look at what `lpn-libs-v2` keeps).
- That the browser really refuses a file with a wrong fingerprint: the checks only show every address has a hash, and `tests/sri.js` that the hashes match the CDNs.
- A real harmful PDF: the PDF safety checks only show that the pinned pdf.js version is outside the known bad ranges, not how pdf.js behaves with a crafted file.
- The demo video actually playing in a browser: `npm test` only shows the player and its source. The weekly health check decodes the live `demo.mp4` with `ffmpeg`, but nothing tests playback in a phone browser or the "couldn’t play" message.
- Whether the demo video's content matches the app: the screen fingerprint only compares seven parts of the log view and the two manifest check results at 390px, and only warns. Changes elsewhere (Settings, export, the side panel) or in the scenes `record.mjs` plays are not compared.
- pdf.js on older phones: the checks use Chromium only, so the browser versions the legacy build needs (roughly iOS/Safari 16.4+, Chrome 94+, Firefox 93+) are not tested.
- How phone apps open the files, the share sheet and printing.
- The per-file notes with real photos and PDFs: the checks use a stand-in `readPhoto()` and call `extractLpns()` and `readNote()` directly. `lpnsFromText()`'s skipped list and the `ocr` and `pdf` problem log entries are not checked, and neither is downloading the problem report on a real phone.
- Files that libraries fetch for themselves at run time (for example Tesseract's worker and language data) are not in the health check's CDN list, because only URLs written in the scripts are checked.

- The feedback Worker on Cloudflare and the real GitHub API: the checks run `worker.mjs` in Node with stand-ins for GitHub and the Durable Object store. The deploy workflow checks that the deployed Worker answers `OPTIONS /report` with 204 (up to 2 minutes), and, only when run by hand with **Also send a test report** ticked, that a real report makes an issue. Sending from the app itself to the live Worker is not checked automatically; the app check only confirms the address is allowed by the security policy.

- The Undo bar staying while it has focus, and its 20-second timer.
- Build 48: a real phone torch (the checks use a stand-in track that reports a torch and records `applyConstraints()`), the torch failure messages and the `scan` problem log entry, the ZXing path calling `torchSetup()`, and the seal note being announced by screen readers.
